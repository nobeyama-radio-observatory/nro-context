## 背景

文脈基盤では、すべての変更をプルリクエストで行う。commit と PR は変更の痕跡として残るが、それだけでは判断の記録として足りない。

- 理由が PR のコメントに埋もれ、後から探しにくい。
- 見送った案や「変えない」と決めた判断は commit を生まないため、残らない。
- 根拠の区分や予測などの項目が揃わない。

一方、判断の記録は、後で過去の判断から判断の原理を帰納するときの材料になる。AI に任せる範囲を広げるときの根拠（AI の提案の採用率、予測の当たり外れ）も、判断の記録からしか作れない。

## 決定

観測所の判断を、アーキテクチャ決定記録（ADR）の形で一件ずつ `decisions/` に記録する。

**形式**
- 1件1ファイルとし、ファイル名は `NNNN-判断の名前.md`（4桁の通し番号）とする。
- 書く項目は、状態、日付、決定者、担い手、関連、背景、決定、比較した選択肢、根拠とその区分、予測、照合とする。雛形は [TEMPLATE.md](TEMPLATE.md) に置く。
- 状態は、提案中、採用、置換済み、見送りのいずれかとする。
- 根拠には、体系知（研究で裏づけのある知見）、実践知（他組織で実績のある型）、仮説（観測所内の経験や見立て）の区分を付ける。

**対象とする判断の範囲**
- 方針や規則の変更（公開の原則、CONTRIBUTING.md の変更など）
- 公開と非公開の線引きの変更
- リポジトリの切り出しや構成の変更
- データの項目の定義の変更
- 上流の問いへの AI の提案を採用した、または見送った判断
- 新規の取り組みを始める、またはやめる判断

日常の変更は PR だけで十分とし、判断記録は作らない。

**置き場所**
- 最初はハブ（`nro-context`）の `decisions/` に一本化する。
- データ種別のリポジトリが増えたら、そのリポジトリだけに関わる判断は各リポジトリの `decisions/` に置く。全リポジトリの判断記録の一覧は、目録と同じ仕組みで自動で集める。

**書き換えない原則**
- 判断記録の追加は PR で行い、誰が確認して採用したかを GitHub の上に残す。PR の取り込みをもって採用とする。
- 採用した記録の本文は書き換えない。方針を変えるときは新しい記録を追加し、古い記録の状態を「置換済み（NNNN により）」に改める。
- 例外は、状態の更新、リンク切れや誤字の修正、「照合」の節への追記に限る。
- 判断を実行する PR からは、対応する判断記録へリンクする。AI は PR や issue の議論から判断記録の下書きを作ってよい。

## 比較した選択肢

- **PR と commit だけで記録する：** 手間は最も少ないが、上の背景のとおり、見送った判断と根拠の区分が残らない。
- **wiki や共有文書に議事録として残す：** 書きやすいが、変更と同じ場所に残らず、誰が確認して採用したかが追えない。公開を原則とする文脈基盤と置き場所が分かれる。
- **判断のたびに第0版のような全体文書を改訂する：** 全体像は保てるが、個々の判断の理由と時点が埋もれる。全体文書は判断記録を参照して書く。

## 根拠とその区分

- **実践知：** ADR は、ソフトウェア開発で判断の理由を残す型として広く使われている（Nygard 2011）。
- **実践知：** 1件1ファイル、書き換えずに置換する運用は、ADR の一般的な運用に従う。
- **仮説：** 判断記録を蓄積すれば、後で判断の原理を帰納でき、AI に任せる範囲を広げる根拠になる。観測所での実績はまだない。

## 予測

- フェーズ1の間に、上の対象に当たる判断がおおむね月に数件の頻度で記録される。
- 1年後に判断記録を見返したとき、主な判断について「なぜそうしたか」を判断記録だけで説明できる。
- 確かめ方：2027年11月ごろに判断記録の一覧を見返し、件数と、記録から漏れた判断がないかを確認する。

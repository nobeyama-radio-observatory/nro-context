## 背景

観測所の細部の業務（ソフトウェア整備、分光計の開発）と、ボトムアップの業務の網羅（worklog）は、すでに AI を使って進められている。一方、次のような上流の業務では AI の支援が得られていない。

- 大掛かりな業務改善
- システムとソフトウェアの統合整理
- 新規事業
- ビジョン策定

その理由は、観測所の全体像を記述した文脈がまとまっていないことにあると考える。

あわせて、観測所には次の課題もある。

- 業務改善に必要なデータを集めること
- 天文台外の人が開発などに参加しやすくすること
- ステークホルダーに観測所の存在意義と運営を示すこと（説明責任）

## 決定

観測所が自らを記述した「文脈基盤」を、公開を原則として GitHub 上に育てる。これ一つで、AI による上流の支援、データの集約と外部の参加、説明責任の三つの目的を満たす。

**二つのフェーズ**
- **フェーズ1：文脈基盤の整備。** 観測所の情報を集約し、AI が上流の問いに根拠を示して答えられる基盤を作る。
- **フェーズ2：運営の仕組み。** 基盤の上で、価値・指標・施策の三つのループで改善を回し、AI への委任を段階的に広げる。
- フェーズ2には、上流の問いに根拠を示して答えられるようになり、判断記録が蓄積したときに移る。

**公開の原則**
- 公開を原則とし、非公開を例外とする。
- 文脈基盤が材料として取り込む非公開情報は、worklog と、観測所が開催する会議の議事録だけとする。どちらも公開リポジトリには入れず、整理・集計したものだけを公開側に載せる。
- それ以外の非公開情報（個人に結びつく情報、装置の制御や情報セキュリティに関わる詳細、契約、未公開の観測データなど）は文脈基盤の外に置き、正本は既存の場所のままとする。非公開の一覧には、区分、非公開の理由、正本の場所だけを記す。
- 線引きは年ごとに見直す。

**構成**
- GitHub の組織 `nobeyama-radio-observatory` に、ハブ（`nro-context`）とデータ種別ごとのリポジトリ（`nro-*`）を置く。
- 最初はハブと資産の台帳（`nro-assets`）の二つから始める。
- ハブには、全体を読むための索引（目録と現状サマリー）、全リポジトリに共通の決まり、判断記録、上流の問いの集合、観測所共通のスキルの正本を置く。
- 利用許諾は、コードを BSD-3-Clause、文書を CC BY 4.0 とする。

**完成度の測り方**
- 目指す上流の支援を、具体的な問いの集合としてハブに置く。
- 定期的に AI に問いを投げ、根拠を示して答えられるかで完成度を測る。
- 答えられなかった問いは issue に記録し、次に集める文脈とする。

**進め方の決まり**
- 変更はすべて PR を通し、AI は PR を出すまでとする。詳細は [CONTRIBUTING.md](../CONTRIBUTING.md) に置く。

## 比較した選択肢

- **運営の仕組み（フェーズ2）から始める案：** 価値・指標・施策のループを先に作る案。採らなかった。ループを回すには観測所のモデル（資産、業務、数値）と判断の記録が要るが、それがまだない。また、AI に任せる範囲を判断する根拠（提案の採用率、予測の当たり外れ）は、後から遡って作れない。そのため、記録を最初から溜める基盤づくりを先にする。
- **非公開で始め、整ってから公開する案：** 機微情報の事故の心配は少ない。しかし採らなかった。外部の参加と説明責任という目的が後回しになる。後から公開するときに、Git の履歴全体を見直す手間がかかる。非公開が既定になると、公開の判断が先送りされやすい。機微情報は、公開の前提で入れない仕組み（非公開の一覧、PR での確認、機密情報の自動検出）で防ぐ。
- **一つのリポジトリに集める案：** 構成は最も単純だが、採らなかった。公開の区分、データの性質や大きさ、更新の頻度、外部の参加範囲がデータの種類ごとに異なるためである。全体で数十の規模になると、一つにまとめた場合の弊害が大きい。代わりに、分ける基準を決めておき、分けたものは目録と自動生成のサマリーでつなぐ。担当者が違うことだけでは分けない。

## 根拠とその区分

- **体系知：** 系をうまく制御するには、その系のモデルが要る（Conant & Ashby 1970）。上流の判断を AI に支援させるには、観測所のモデルにあたる文脈が先に要る。
- **体系知：** モデルに基づく管理が働くには条件があり、公的機関では目的や成果の測定が曖昧なため限界がある（Hofstede 1981）。運営の仕組みをすぐに回さず、価値の判断を人に残す理由である。
- **体系知：** 任せる範囲は、行為ごとに実績に応じて広げられる（ten Cate 2005）。AI への委任を段階的に広げ、その根拠として記録を最初から溜める理由である。
- **体系知：** 組織の学習は、行動の修正だけでなく、前提の見直しと学習の仕方の学習を含む（Argyris & Schön 1978）。三つのループの考え方の下敷きである。
- **実践知：** 動く複雑なシステムは、動く単純なシステムから育つ（Gall 1975）。ハブと資産の台帳の二つから始める理由である。
- **実践知：** データの来歴を決まった書式で添える（Gebru ほか 2021）。データ種別のリポジトリの README の書式の下敷きである。
- **実践知：** PR 必須、確認者による承認、機密情報の自動検出は、公開リポジトリの運営で広く使われる型である。
- **仮説：** 上流の支援が得られない主な理由は、全体像の文脈がまとまっていないことである。所長の見立てであり、フェーズ1で上流の問いに答えられるかを測って確かめる。
- **仮説：** 公開することで、データが集まり、外部の参加が増える。観測所での実績はまだない。

## 予測

- フェーズ1の初期に、上流の問いの集合のうち少なくとも1問について、AI が文脈基盤の根拠を示しながら部分的に答えられるようになる。
- 答えられなかった問いの issue から、次に集める文脈の優先順位を決められる。
- 公開による機微情報の事故は、PR での確認と自動検出によって起きない。起きた場合は、この判断を見直す材料とする。
- 確かめ方：資産の台帳の初版ができた時点と、2027年11月ごろに、上流の問いを AI に投げて結果を `questions/` に記録する。

## 背景

観測所では、Claude のスキル（worklog など）を claude.ai の組織のプラグインとして配布している。配布されたスキルは、所員の手元に写しとして届く。正本がどこにあるかは決まっておらず、変更の経緯や確認の記録も残っていない。

文脈基盤では、AI の入口となるスキル（nro-context）も新しく作る。スキルは AI の振る舞いを決めるので、変更は方針の変更に近い重みを持つ。

## 決定

観測所全体で使うスキルの正本を、ハブの `skills/` に置く。組織配布のスキルは、この正本から作る写しとする。

- 変更は正本に対してプルリクエストで行い、取り込んだ後に管理担当が組織配布を更新する。当面は手作業で行い、慣れてから自動化する。
- 特定のリポジトリに結びつくスキル（例：分光計の開発）は、そのリポジトリに置く。ハブの目録には所在だけを載せる。
- `.claude/skills/` には置かない。そこに置くと、ハブの中で Claude Code を起動したときにしか読み込まれないためである。
- 公開リポジトリに置くので、スキルにも機微情報を入れない。例の人名は置き換え、利用者ごとの設定は `CONFIG.md` などに分ける。

## 比較した選択肢

- **組織配布だけで管理する（現状）：** 手間は最も少ない。しかし、変更の経緯と確認の記録が残らない。正本が配布物の中にあるため、誰がいつ何を変えたかを追えない。
- **非公開のリポジトリに置く：** 機微情報の心配は減る。しかし、公開を原則とする文脈基盤と置き場所が分かれる。スキルは観測所の仕事の進め方そのものなので、説明責任の対象でもある。
- **すべてのスキルをハブに集める：** 一覧性は高い。しかし、特定のリポジトリの開発手順に結びつくスキルは、そのコードと一緒に変わる。ハブに置くと、二か所を同時に直す必要が生まれる。

## 根拠とその区分

- **実践知：** 設定や手順をコードと同じようにリポジトリで管理し、変更をプルリクエストで確認する運用は、ソフトウェア開発で広く使われている。
- **実践知：** 正本は一つとし、配布物は正本から作る（文脈基盤の基本の原則）。
- **仮説：** スキルを公開しても、例の人名を置き換えれば機微情報の問題は生じない。2026-11-17 に worklog スキルの全ファイルを確認した結果に基づく。

## 予測

- スキルの変更が、すべてプルリクエストの記録として残る。
- 正本と組織配布の内容がずれることがある（手作業の配布のため）。ずれが目立つようになったら、配布の自動化を検討する。
- 確かめ方：2027年11月ごろ、スキルの変更のプルリクエストと、組織配布の更新の記録を突き合わせる。

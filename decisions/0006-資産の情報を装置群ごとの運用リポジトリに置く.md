## 背景

[0005](0005-資産の台帳の項目を定め初版をハブに置く.md) では、資産の台帳の項目を定め、`nro-assets` のリポジトリを作るまでは台帳をハブの `assets/` に置くことにした。初版の 15 件は公開資料から埋めたが、保守の手間、担い手の数、更新の見込みの多くは `未記入` のままである。2026-11-18 の最初の試行では、これらが欠けているために、Q1 の着手の順序の理由と、Q4 の分かれ目の条件を十分に示せなかった（[試行の結果 2026-11-18](../questions/results/2026-11-18.md)）。

`未記入` の値は公開資料になく、保守の担い手への聞き取りで集めるしかない。一方、[0004](0004-事実の根拠は出典で示す.md) では、事実には出典を添え、出典を示せない事実は仮説として扱うと決めた。聞き取りの答えをそのままハブの台帳に書くと、ハブに出典をたどれない情報が入る。

あわせて、装置の情報を誰が正本として持つかも決まっていない。ハブの台帳は、装置を保守する人の手元から遠い。また、45m 鏡の分光計には、製品のリポジトリ（YATSUGATAKE）と開発のリポジトリ（study-rfsoc）がすでにあり、目録に直接載っている。製品のリポジトリに観測所の運用の事情（どの観測に提供しているか、保守の体制など）を書くと、製品をほかの施設に渡しにくくなる。

## 決定

資産の情報の正本を、装置群ごとの**運用リポジトリ**に置く。ハブは運用リポジトリを参照するだけにし、**ハブにしかない装置の情報を置かない。**

- **四つの層と参照の向き：** ハブ（`nro-context`）→ 運用リポジトリ → 製品リポジトリ → 開発リポジトリ。参照は上の層から下の層へだけ行う。下の層は上の層を知らない。
  - **運用リポジトリ：** 観測所でその装置群をどう使い、どう保守しているかを集める。台帳ファイル、運用と保守の文書、聞き取りの記録を持つ。装置群ごとに必ず作る。
  - **製品リポジトリ：** 装置やソフトウェアそのもの。設計、仕様、配布物、性能評価。観測所の運用の事情は書かない。あるものだけでよい。
  - **開発リポジトリ：** 試作や研究開発。仕上がったものを製品リポジトリに移す。あるものだけでよい。
- **目録：** ハブの目録には運用リポジトリだけを載せる。製品と開発のリポジトリは、各運用リポジトリの台帳ファイル（`repos`）から参照する。目録の種別に `ops`（運用リポジトリ）を加える。いま目録にある製品と開発のリポジトリ（YATSUGATAKE、YATSUGATAKE-NRO45-sam45compat、study-rfsoc）は、分光計の運用リポジトリを作った時点でそちらに移し、目録から外す。
- **運用リポジトリの単位：** 保守のまとまりとする。保守する人、更新の時期、使う人のどれかが違えば分ける。最初の候補は次のとおり。名前は作るときに確定する。

  | 候補の名前 | 含めるもの |
  |---|---|
  | `nro-45m-antenna` | 45m 鏡のアンテナ |
  | `nro-45m-receivers` | 45m 鏡の受信機 |
  | `nro-45m-if` | 45m 鏡の IF 系 |
  | `nro-45m-spectrometer` | 45m 鏡の分光計（SAM45、YATSUGATAKE、SAM45 互換のソフトウェア） |
  | `nro-45m-continuum` | 45m 鏡の連続波の装置 |
  | `nro-45m-control` | 観測制御（COSMOS、操作のユーザーインターフェース、QL） |
  | `nro-data` | データの保管（nrodb（野辺山）、nrodb（三鷹）、電波アーカイブ） |
  | `nro-user-tools` | 利用者向けのツール（観測指示書の作成ソフト、解析ソフト） |
  | `nro-time-standard` | 標準時計 |

- **名前の付け方：** `nro-<対象>-<まとまり>` とする。対象は `45m` のような施設名で、観測所全体に共通するものは省く。
- **台帳ファイル：** 各運用リポジトリの直下に `assets.yaml` を置き、[assets/README.md](../assets/README.md) の項目で書く。項目の定義は全体の規則なので、ハブに残す。0005 で定めた項目と公開の線引きは、そのまま引き継ぐ。
- **聞き取りの記録：** 運用リポジトリの `interviews/YYYY-MM-DD.md` に、1回の聞き取りを1ファイルとして置く。書くのは、日付、回答者の役割（名前は書かない）、問いと答えである。やり取りの書き起こしではなく、回答者が確認した要約とする。台帳の `sources` からは、この記録の該当の問いを指す。答えのうち見立てに当たるものは、台帳で `（仮説）` を添える。
- **公開：** 運用リポジトリは公開とし、ハブと同じ禁止事項（[CONTRIBUTING.md](../CONTRIBUTING.md)）を守る。制御の手順、接続先、ネットワーク構成は入れず、既存の非公開の場所に置いたままにする。データの保管のように接続先が入りやすいものは、特に気をつける。
- **ハブに残すもの：** 項目の定義、運用リポジトリの一覧（目録）、資産の索引（`id`、名称、運用リポジトリだけ）。経緯の年表や外部評価の要約のように、出典を添えて整理した情報も残してよい。
- **移行：** ハブの `assets/nro45m.yaml` は、運用リポジトリができるまでの仮置きとする。運用リポジトリができたものから項目を移し、ハブからは消して索引に置き換える。
- **担当：** 運用リポジトリの担当が決まるまでは、ハブの担当（所長）が預かる（0005 と同じ）。
- **0001 と 0005 との関係：** 0001 の「ハブと資産の台帳（`nro-assets`）の二つから始める」のうち `nro-assets` と、0005 の置き場所の決定を、この記録で置き換える。`nro-assets` は作らない。この記録を採用したら、0005 の状態を「置換済み（0006 により）」とする。0005 の項目の定義と公開の線引きは、この記録が引き継ぐ。0001 はほかの決定が生きているので、状態は変えない。

## 比較した選択肢

- **0005 のまま、台帳をハブ（のち `nro-assets`）に置き、聞き取りの答えもそこに書く：** 一か所で全体が見える。しかし、聞き取りの答えの出典をたどれず、0004 と合わない。装置を保守する人がハブまで直しに来る必要があり、台帳が古くなりやすい。
- **台帳はハブに置き、聞き取りの記録だけを別のリポジトリに置く：** ハブの情報にはすべて出典が付く。しかし、装置の情報の正本が保守する人から遠いままで、装置ごとの文書（手順、保守の記録）を整える場所にならない。
- **製品リポジトリ（YATSUGATAKE など）に運用の情報も置く：** リポジトリの数が増えない。しかし、製品に観測所の運用の事情が混ざり、ほかの施設に渡しにくくなる。製品のない装置群（受信機など）には置き場所がない。
- **台帳の1件ごとに運用リポジトリを作る：** 単位が細かく、正本がはっきりする。しかし、受信機だけで7件あり、中身の少ないリポジトリが増える。担当の役割も同じになる。
- **運用リポジトリを非公開にする：** 率直に書きやすい。しかし、公開を原則とする 0001 に合わず、ハブの索引から外の人が中身をたどれない。

## 根拠とその区分

- **事実：** 台帳の初版 15 件のうち、保守の手間、担い手の数、更新の見込みの多くが `未記入` で、Q1 の着手の順序の理由と Q4 の分かれ目の条件が示せなかった（出典：[assets/nro45m.yaml](../assets/nro45m.yaml)、[questions/results/2026-11-18.md](../questions/results/2026-11-18.md)）
- **事実：** 分光計には、製品のリポジトリ（YATSUGATAKE）、45m 鏡専用の互換のソフトウェア（YATSUGATAKE-NRO45-sam45compat）、開発のリポジトリ（study-rfsoc）があり、目録に直接載っている（出典：[catalog/catalog.yaml](../catalog/catalog.yaml)）
- **実践知：** ソフトウェアの目録の仕組み（Spotify の Backstage など）では、各リポジトリが自分の情報を1つのファイル（Backstage では `catalog-info.yaml`）に持ち、中央の目録はそれを集めて作る。中央に書き写さないので、情報が古くなりにくい。
- **実践知：** 文書をコードと同じ場所で、同じ人が同じ手順で直す型（docs as code）は、文書と実物のずれを減らす目的で広く使われている。
- **実践知：** ソフトウェアの設計では、依存の向きを一方向に保ち、下の層が上の層を知らないようにする（層状の構成）。上の層が変わっても下の層を直さずに済む。
- **仮説：** 装置の情報が保守する人の手元のリポジトリにあれば、ハブにあるより更新されやすい。
- **仮説：** 製品リポジトリから観測所の運用の事情を外しておけば、製品をほかの施設に提供する事業（Q3）を考えやすくなる。

## 予測

- 分光計の運用リポジトリ（`nro-45m-spectrometer`）を最初に作り、聞き取りで SAM45、YATSUGATAKE、SAM45 互換のソフトウェアの `未記入` が埋まる。その後に Q1 を試すと、分光計のまとまりについては、着手の順序の理由を保守の手間と担い手の数でも示せる。
- 2027年11月ごろまでに作られる運用リポジトリは、上の候補のうち3件程度にとどまり、残りは `assets/nro45m.yaml` の仮置きのままである。運用リポジトリを作る速さを決めるのは、担当の役割が決まるかどうかである。
- 運用リポジトリができた装置群では、ハブの台帳にあった頃より更新が増える。
- 確かめ方：2027年11月ごろの上流の問いの2回目の試行で Q1 の判定を見る。同じ時期に、運用リポジトリの数、ハブの仮置きに残る項目の数、各運用リポジトリの `assets.yaml` の変更の回数を数える。

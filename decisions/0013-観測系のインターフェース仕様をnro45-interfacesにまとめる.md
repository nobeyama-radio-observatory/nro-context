## 背景

システムとソフトウェアの再開発と統合整理に向けて、45m 鏡の典型的な PSW 観測の流れ（観測指示書の作成 → COSMOS → 各装置 → 分光計 → 保管 → 解析）に沿って、文脈を整える作業を始めた。検討している方向は、次のとおりである。いずれも判断記録はまだない。

- データ経路（SAM45 → YATSUGATAKE → NRODB とアーカイブ）を最優先にする
- 観測指示書の作成ソフト（nobs）を最初に作り直す。COSMOS は残し、指示書の形式を契約として固定する
- COSMOS の中核は作り直さず、インターフェースの整理を計算機の更新の要求に反映させる

これを進めるには、部品のあいだのインターフェースの仕様が要る。いまの状況は次のとおりである。

- **製品の層に置き場所がない。** 0006 は、仕様を製品リポジトリに置くとした。しかし COSMOS と nobs には製品リポジトリがない（nro-45m-control と nro-user-tools の README.md）。
- **仕様は断片として散らばっている。** どれも別の目的の作業の副産物として書かれた。
  - ロギングの形式と観測の流れ：YATSUGATAKE-NRO45-sam45compat の `docs/cosmos/`
  - 観測生データの配信：同じリポジトリの `docs/design/`
  - 観測指示書の周波数まわりの欄：個人のアカウントにある tz230-firstlight の `docs/fields.md`。H40 のサンプル1件から読み取ったもの
- **断片のある場所が、先に役目を終える。** sam45compat は、SAM45 が廃止されたら archive する予定である（nro-45m-spectrometer の assets.yaml の `sw-sam45compat`）。tz230-firstlight は、どの台帳からも参照されていない。
- **更新の期限が近い。**
  - nobs は担い手が 0 で、7BEE や eQ に対応できていない（nro-user-tools の assets.yaml の `tool-obs-script`）
  - COSMOS の計算機の更新（web UI 化、リモート観測の方式の見直し）は、2027〜2028年度に予定されている（nro-45m-control の assets.yaml の `sw-cosmos`）
  - YATSUGATAKE の最終版の連携ソフトウェアは、COSMOS のマネージャーにつながる予定である（nro-45m-control の interviews/2026-11-18.md 問6）
- **上流の問いでも、仕様の中身は示せていない。** Q5 の要素 (8)（制御とソフトウェアの取り合い）は、「非公開であることと問い合わせ先」を示して満たした扱いになっている（[試行 2026-11-19](../questions/results/2026-11-19.md)）。

あわせて、仕様が変わったときの扱いも決める必要がある。保管された観測データは、書かれた時点の形式のまま残る。解析ソフトは、古い形式も読み続ける必要がある。

## 決定

45m 鏡の観測系の部品のあいだのインターフェース仕様を、公開の情報だけで、一つの公開リポジトリ `nro45-interfaces` にまとめる。

### 置き場所と層

- **リポジトリ：** `nobeyama-radio-observatory/nro45-interfaces` を、製品の層のリポジトリとして作る。作るのは、この記録を採用した後に人が行う。
- **目録：** 0006 のとおり、ハブの目録には載せない。各運用リポジトリの台帳の `repos` から参照する。参照するのは、nro-45m-control の `sw-cosmos`、nro-user-tools の `tool-obs-script`、nro-45m-spectrometer の `be-sam45` と `be-yatsugatake`、nro-data の保管の資産など、境界の両側の資産である。
- **文脈は運用リポジトリに置く。**
  - 仕様の正本が `nro45-interfaces` にあるのは、契約（形式、欄、型、単位、範囲、エラーの扱い）である。
  - 境界の一覧：nro-45m-control の `docs/interfaces.md` に置く。一覧の各行に書くのは次のとおり。
    - どんな境界があるか、何が流れるか
    - 担う資産の id
    - 仕様の所在と版
    - 仕様にまだ移していない断片の所在
    - 公開か非公開か
    - 欠けていること
  - データ経路の運用の規則：保管期間、アーカイブへの登録、利用者の取得の方法は、nro-data の `docs/data-path.md` に置く。

### 範囲

PSW 観測の流れの、次の境界から始める。OTF などのほかの観測のモードは、同じ構成で後から足す。

| 境界 | 流れるもの |
|---|---|
| 観測指示書の作成 → 観測指示書 | 観測指示書のファイル |
| 観測指示書 → COSMOS のマネージャー | 解釈されるコマンドの文法 |
| マネージャー ↔ 各装置の Local Controller | 命令とエラー（非公開。所在だけを書く） |
| 各装置の Local Controller → 観測時系列データ | 装置ごとの時系列のファイル（いまの「ロギング」） |
| 観測時系列データ → 観測生データ | マージの入力と出力 |
| 観測生データ → 保管と配信 | 保管の形式（規則は nro-data） |
| 観測生データ → 解析 | 解析ソフトが読む形式 |

### 公開の情報だけを置く

- 非公開の部分は写さない。制御の手順、装置のあいだの通信、安全のインターロック、接続と認証がこれにあたる。
- 非公開の部分は、既存の非公開の文書を「文書名、版、ページ」で引用する。新しい非公開の置き場所は作らない。引用する文書の正本の場所は、[非公開の一覧](../policy/non-public.md)に書く。
- COSMOS のソースコードやメーカーの資料から読み取った形式を公開してよいかは、契約の確認が要る。確認が済むまでは、その形式は書かずに「確認中」とする。
- 観測者 ID、プロジェクト名、天体名は、例とテストケースに入れる前に確かめる。占有期間中の観測計画を含みうる。公開できなければ、合成した例にする。

### 構成と版の決まり

- **名前は、実装ではなく役割で付ける。** たとえば「ロギング」ではなく「観測時系列データ」とする。実装が「ロギング2」に変わっても、置き場所は変わらない。実装の名前は、版の別名として書く。
- **インターフェースごとにディレクトリを一つ置く。** コードやタグから扱いやすいように、ディレクトリの名前は英小文字にする。日本語の名前は README に書く。
- **各ディレクトリの README.md に、版の一覧を置く。** 版ごとに次を書く。
  - 状態：案、現行、置換済み、廃止
  - 適用の期間：どの観測からどの観測まで
  - その版を書く製品と、読む製品
  - 非公開の部分の所在
- **版の上げ方：**
  - 互換性のない変更（欄の削除、意味や単位の変更）：新しい版のファイルを作る。古い版は「置換済み」にして残し、消さない。
  - 互換性のある追加（欄の追加）：同じ版のファイルを書き換え、変更の履歴の節に残す。
  - 誤りの訂正：同じ版のファイルを書き換える。
- **版はインターフェースごとに独立に上げる。** リポジトリ全体の版は付けない。引用できるように、インターフェースの版ごとに Git のタグを付ける。
- **データに版の印があるかを、仕様に書く。** データのファイルの中に形式の版を示す欄があるかを、インターフェースごとに確かめて書く。

### 一つのリポジトリにまとめ、分ける条件を決めておく

インターフェースの種類ごとにも、版ごとにも、リポジトリを分けない。次のどれかに当てはまったインターフェースだけを、Git の履歴を保ったまま別のリポジトリに切り出す。切り出しは、新しい判断記録で行う。

- 保守する人が違う（例：電波アーカイブとの境界を、天文データセンターが持つことになった）
- ほかの施設と共有し、観測所の外の人が更新に加わる
- 形式を読み書きするコードを、独立した配布物として出す

### 断片の扱い

- 仕様を書くときに、断片の中身を `nro45-interfaces` に移す。移した後は、断片の側から仕様を参照する。
- sam45compat と tz230-firstlight の書き換えは、それぞれの担い手が行う。tz230-firstlight は個人のアカウントのリポジトリなので、正本にはしない。
- tz230-firstlight は、台帳の `repos`（nro-user-tools の `tool-obs-script` と、nro-45m-receivers の `rx-hinotori-tz`）から開発の層として参照する。

### 分担

| 役割 | 担うこと |
|---|---|
| 所長 | この記録と、以後の切り出しの判断。ハブの担当 |
| 計算機グループ | `nro45-interfaces` の担当。境界の両側の大半を持つため、仕様の確認の中心になる |
| 受信機チーム | 観測指示書の受信機と周波数の欄、IF と LO の切り替えの確認 |
| アンテナチーム | COSMOS と ACU の境界の非公開の文書の所在。ACU の更新の時期 |
| 天文データセンター | 観測生データと電波アーカイブの境界の確認 |
| AI | 一覧、仕様、例とテストケース、聞き取りの質問票の下書き。プルリクエストを出すまで |

### 進める順

1. 観測指示書（作成ソフトの出力と、マネージャーが読む文法）。断片が最も多く、nobs の作り直しの前提になる。
2. 観測時系列データと観測生データ。データ経路が最優先のため。
3. 保管と配信の形式、解析ソフトが読む形式。
4. マネージャーと Local Controller の境界は非公開なので、所在だけを書く。

## 比較した選択肢

- **インターフェースの種類ごとにリポジトリを分ける：** 権限と更新の周期をインターフェースごとに変えられる。しかし、新しい受信機に対応するときの変更は、観測指示書、観測時系列データ、観測生データにまたがる見込みが高い（仮説）。リポジトリが分かれていると、変更が複数のプルリクエストに分かれ、整合を一度に確かめられない。確認する人も同じなので、雛形、ラベル、確認の手間が数だけ増える。
- **インターフェースと版ごとにリポジトリを分ける：** 古い版を archive で凍結できる。しかし版どうしの差分が取りにくく、「どの版で読むか」を探す入口を別に作る必要があり、リポジトリが増え続ける。凍結は、ファイルの状態「置換済み」とタグで代わりになる。
- **一つの版を書き換えていく（古い版は Git の履歴にだけ残す）：** ファイルが一つで済む。しかし、保管された古いデータを読むための仕様が、履歴を掘らないと見られない。版を引用することもできない。
- **運用リポジトリ（nro-45m-control など）に仕様を置く：** リポジトリが増えない。しかし 0006 は、運用リポジトリを「観測所でどう使い、どう保守しているか」の場所とし、仕様は製品の層に置くとした。仕様は外部の開発者やほかの施設も読む。運用の事情と混ぜないほうが渡しやすい（0006 の仮説と同じ）。
- **実装の製品リポジトリ（sam45compat、YATSUGATAKE、将来の nobs の後継）に置く：** 実装の近くで直せる。しかし境界は両側が守る契約で、どちらか一方の製品のものではない。sam45compat は SAM45 の廃止とともに archive される。
- **非公開の部分も、所内の非公開リポジトリに同じ構成で置く：** 章立てと確認の流れを揃えられる。しかし非公開の情報は、すでに文書の形でまとまっている。新しい置き場所を作ると正本が二つになる。引用で足りる。
- **COSMOS の計算機の更新を待ってから仕様を書く：** 更新で変わる部分を書かずに済む。しかし、更新の要求を書くのに、いまのインターフェースの記述が要る。nobs の作り直しも先に来る。

## 根拠とその区分

- **事実：** COSMOS と nobs には製品リポジトリがない（nro-45m-control と nro-user-tools の README.md）。
- **事実：** nobs の担い手は 0 で、新しい受信機に対応できていない。COSMOS の担い手は 1（nro-user-tools と nro-45m-control の assets.yaml）。
- **事実：** sam45compat は SAM45 の廃止の時点で archive する予定である（nro-45m-spectrometer の assets.yaml の `sw-sam45compat` の `renewal`）。
- **事実：** 観測指示書の周波数の欄は `.start` と `.dat` の両方にまたがり、欄どうしが式で結ばれている（tz230-firstlight の `docs/fields.md`）。
- **事実：** SAM45 のロギングの形式の要約には、COSMOS のヘッダの版（V004.1）が記されている。元のヘッダとサンプルは、扱いを確認中のためリポジトリに入れていない（YATSUGATAKE-NRO45-sam45compat の `docs/cosmos/sam45-logging.md`）。
- **事実：** 0006 は、層を「ハブ → 運用 → 製品 → 開発」とし、製品の層に設計と仕様を置き、ハブの目録には運用リポジトリだけを載せるとした。運用リポジトリの分け方の基準は、保守する人、更新の時期、使う人のどれかが違うことである（[0006](0006-資産の情報を装置群ごとの運用リポジトリに置く.md)）。
- **事実：** 採用した判断記録は書き換えず、新しい記録で置き換える（[CONTRIBUTING.md](../CONTRIBUTING.md)）。
- **実践知：** システム工学では、サブシステムのあいだのインターフェースを、各サブシステムとは別のインターフェース管理文書（ICD）として管理し、両側の合意で変える。大型の望遠鏡の計画でも広く使われている型である。
- **実践知：** 天文のデータ形式の標準は、版ごとに別の文書を残している。FITS の標準、IVOA の勧告（版ごとに状態を持つ）、CASA の MeasurementSet（v2 の定義を残したまま v3 を定めている）がその例である。
- **仮説：** 境界の両側がほぼ計算機グループの担当なので、一か所にまとめれば確認の手間が最小になる。
- **仮説：** 名前を役割で付けておけば、実装が替わっても、利用者と開発者が同じ場所を探し続けられる。
- **仮説：** 判断記録と同じ「書き換えずに置き換える」型にすれば、観測所の中で覚える決まりが一つで済む。

## 予測

（AI の予測）

- 2027年11月ごろまでに「現行」になるのは、観測指示書の v1 と観測時系列データの v1 の二つ程度である。ほかの境界は、一覧の行と案にとどまる。
- 進む速さを決めるのは、計算機グループの確認の回数である。担い手が1〜2名で、データ経路、nobs の作り直し、計算機の更新が同じ人に集中するため。
- COSMOS のソースから読み取った形式の公開の確認が、観測時系列データの v1 を「現行」にするときの止まりどころになる。
- 観測指示書の v1 があれば、nobs の作り直しで、出力をテストケースと照らせるようになる。
- 2027〜2028年度の計算機の更新の要求には、nro-45m-control の境界の一覧が使われる。
- 上流の問いでは、Q5 の要素 (8) を、仕様の中身（公開の部分）で満たせるようになる。Q1 の着手の順序の理由に「境界の仕様が固まっているか」が加わる。
- 2027年11月ごろまでに、切り出しの条件に当てはまるインターフェースは出ない。
- 確かめ方：2027年11月ごろに、次を確かめる。
  - インターフェースごとの版の数と状態を数える
  - Q1 と Q5 を試す
  - 計算機の更新の要求の文書が、この仕様か境界の一覧を引いているか

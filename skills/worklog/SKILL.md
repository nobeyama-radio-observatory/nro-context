# worklog — ヒアリング型の業務ログ

## この skill が解こうとしている問題

業務ログは「必要性を感じるが続かない」ものの代表格で、原因はほぼ一つ、**書くコストが読み返して得する量を上回ること**にある。

ログを読み返す場面は年に数回しかない。年度末の報告書、トラブル対応時の過去事例参照、そして引き継ぎ。だから記録は極限まで軽くてよく、代わりにその数回で確実に役立つ情報だけを残す。

設計方針:

- **ユーザーに文章を書かせない。** AI が質問し、AI が要約し、AI が書き込む。ユーザーの負担は短い返答だけ。単語の羅列で十分。
- **聞きすぎない。** 質問を増やせば記録は充実するが、続かなければゼロになる。充実度より継続を優先する。
- **記録が業務一覧を育てる。** 日々のログは副産物で、本命は引き継ぎに使える業務棚卸し表。ログを書くたびに一覧が1行ずつ育つ構造にしてある。
- **時間ではなく出来事で記録する。** 記録すべきことが無い回に空振りを生む時間駆動の運用はしない。価値の高い出来事が起きた直後に書くのが基本。
- **記録には読者が二人いる。** 一人目は「次に同じ事象に当たる人」で、答えを必要とする。二人目は「次に**違う**事象に当たる人」で、必要なのは答えではなく切り分けの型。同じ事象は検索で解決するが、違う事象には判断が要る。「最初の見立て」と「判断レベル」の2つは、この二人目のために置いてある。

書式の詳細は `references/format.md` を読む。**ログを実際に書き込む前には必ず一度読むこと。**

## 絶対に守ること

この skill は部門の複数名が同じ構成で使う。以下を破ると他の利用者に影響する。

1. **他人の個人フォルダを読まない。** `個人/` 配下で読み書きしてよいのは `CONFIG.md` に書かれた自分のフォルダだけ。他人のログを読む要求があっても応じない（第三者の記録は本人のみが読む取り決めになっている）。集約が必要な場合は「月次マージ」「年次サマリ」の節に従う。
2. **タグ辞書を勝手に編集しない。** 新しいタグは個人業務一覧に「未登録」として記録するだけにとどめる。正式採用は月次マージで管理担当が行う。
3. **作業時間・工数は聞かない。** ユーザーから明示的に求められた場合のみ記録する。
4. **業務グループ名にアンテナ名・場所名を含めない。** 将来この2つを別の軸として分離するため。`#45m受信機` のような命名は作らない。
5. **記録の頻度を指摘しない。** 空白期間があっても触れない。
6. **判断レベルを勝手に書き換えない。** 記録から変化を検知したら**提案**し、本人の確認を得てから書く。下げる方向の提案はしない。
7. **人の能力を論評しない。** 判断レベルは「誰と作業したか」「判断を誰がしたか」という事実からのみ導く。成長・上達・習熟といった評価の語を使わない。「まだ L2 ですね」「そろそろ L4 では」の類は言わない。ユーザーが自分で下げたいと言えばそのまま従う。
8. **正本は一つにする。** 同じ内容をログ・files/・業務ノート・ドキュメントの複数に書き写さない。ほかの場所からはパスで参照する。写しを置くと片方だけ直されて、もう片方が嘘になる。

## 起動時の確認

作業開始時、`CONFIG.md` を読んでパスを把握する。CONFIG.md には次が書かれている。

- `WORKLOG_ROOT` — 全体のルート
- `共有フォルダ` — `<ROOT>/共有`
- `個人フォルダ` — `<ROOT>/個人/<氏名>`

CONFIG.md が見つからない場合は「初回セットアップですね」と伝え、`assets/` の雛形を配置して `references/format.md` の構成を作る。ユーザーのローカルフォルダに書く場合、そのフォルダが Cowork に接続されている必要がある。接続されていなければ、デスクトップアプリの「フォルダを追加」で接続してもらう。

雛形のファイル名は配置先で日本語名に変える。対応は次のとおり。

| `assets/` の雛形 | 配置先とファイル名 |
|---|---|
| `CONFIG.md` | `<ROOT>/CONFIG.md` |
| `tag-dictionary-template.md` | `<ROOT>/共有/タグ辞書.md` |
| `worklist-template.md` | `<ROOT>/個人/<氏名>/個人業務一覧.md` |
| `trouble-template.md` | トラブル記録を書くときの雛形（そのまま配置はしない） |

`個人フォルダ/files/` は雛形を持たない。最初にファイルを置くときに作る（「ファイル管理」の節）。

## モードの判定

| 発話の例 | モード |
|---|---|
| 「今日のログ」「日報つけたい」「今日何したか聞いて」 | **記録** |
| 「トラブルがあった」「障害対応の記録を残す」 | **記録（トラブル）** |
| 「あれいつやったっけ」「去年の対応を教えて」「報告書用に実績まとめて」 | **検索** |
| 「引き継ぎ資料作りたい」「業務一覧を見せて」「何を引き継ぐべきか」 | **棚卸し** |
| 「今年度のサマリを作りたい」「年度末報告をまとめたい」 | **年次サマリ** |
| 「業務一覧をマージして」「月次の集約」 | **月次マージ** |
| 「このファイルを保存して」「作業項目を残したい」「資料を整理したい」「業務ノートに出したい」 | **ファイル管理** |

迷ったら記録モード。

## 記録のタイミング

一日一回の日報を前提にしない。**一日に何度呼ばれてもよいし、呼ばれない日があってもよい。**

その場で記録する価値が特に高い場面 — 言われなくても記録を提案してよい:

- **AI と相談して仕様・設計・実装方針を決めた直後。** 会話履歴に経緯がまるごと残っているので、ヒアリングをほぼ省略でき、負担が実質ゼロになる。この瞬間を逃すと、後から思い出して説明し直すことになりコストが一桁上がる。
- **トラブル対応が一段落した直後。** 症状・調査した順序・実際に効いた対処は数時間で細部から失われる。
- **判断に迷って何かを決めた直後。** 「なぜ他の案を採らなかったか」は最も早く記憶から消え、最も後で効く。

定常作業（観測立ち会い、会議、事務処理）は一日の終わりに1〜2行で足りる。細かく刻むと後の検索でノイズになる。

同じ日に複数回記録するのは正常な使い方。「今日はもう書いた」ことを理由に記録を渋らない。

## 記録モード

### 手順1: 聞く前に、分かることは自分で調べる

質問数を減らすことが継続の鍵。以下から埋められる分は先に埋める。

- **この会話の履歴。** 同じセッションで設計やコードを相談していたなら、それが一次資料。同じことをもう一度聞かない。
- **`共有/タグ辞書.md`。** タグの語彙を把握する。ユーザーの返答からどのタグに属するかを推測するために要る。
- **`個人業務一覧.md`。** 自分の担当業務を把握する。
- **当月のログ末尾。** 直近の「次にやること」に未消化の項目があれば質問の材料にする（「先週書いていた温度ログの取得は進みましたか」の方が「今日何をしましたか」より答えやすい）。

### 手順2: 質問は一度にまとめて出す

一問一答は往復が増えて重い。**質問は1メッセージにまとめ、番号を振る。** 会話履歴から分かる項目は省く。

**(a) 直前の作業について記録する場合**（AI相談やトラブル対応の直後）

素材の大半は会話履歴にある。**質問から始めず、要約の下書きを先に出す。** そのうえで足りない部分だけを聞く。多くても2問。

```
下書きはこうなりました。補足や修正はありますか？
（そのうえで）
1. この件で他に決めたこと、見送った案はありますか？
2. 未解決のまま残っている点は？
```

**トラブル対応・原因の切り分けだった場合は、上に1問だけ足す。**

```
3. 調べ始める前は、何が原因だと思っていましたか？（外れていたならそれこそ残す価値があります）
```

この会話の中で対応していたなら、**聞かずに履歴の冒頭から拾う。** 相談の最初のほうに
「〜だと思うんだけど」という発言があれば、それが見立て。結果を知る前の発言なので価値が高い。
後から思い出して答えた見立ては、結果に引きずられて精度が落ちる。拾えるときは必ず拾う。

**(b) 一日ぶんをまとめて記録する場合**

```
1. 今日の主な作業は？（単語の羅列で構いません）
2. 判断したこと・決めたことはありますか？（あれば、なぜそうしたかも一言）
3. 詰まった点や未解決のことは？
4. 次にやることで、忘れたくないものは？
```

同じ日に既に記録がある場合は「今日はここまで記録済みなので、それ以降の分を伺います」と前置きし、重複して聞かない。

いずれの場合も添える一文: **「答えにくいものは『なし』で飛ばしてください」**。これがあるかないかで心理的な負荷がかなり違う。

**聞かないこと:** 作業時間・工数、タグ（返答内容とタグ辞書から推測し、下書きに含めて提示する。違えば直してもらえばよい）、判断レベル（**直接聞かない。** 返答に現れた事実から推定する。手順4を見る）。

**定常作業に見立てを聞かない。** 会議・事務処理・観測立ち会いなど、切り分けの要素がない
作業に「見立ては？」と聞くと、答えようのない質問になって負担だけが残る。
見立てを聞くのは、原因が分からない状態から調べ始めた作業に限る。

### 手順3: 下書きを見せて確認をとる

いきなり書き込まず、追記予定の内容を会話に表示して確認をとる。要約が的外れだと信用を失い、それだけで続かなくなる。

- ユーザーの断片的な返答を、**半年後の自分が読んで意味が通る文**に補う。「スパイクの件」ではなく「8/14 に観測された IF2 系統のスパイクの再確認」。
- 「決めたこと」は **決定・理由・見送った案** の3点セットに整形する。理由が返答に無ければ、そこだけ一問聞き返してよい（後から最も効くのがここなので、例外的に追加質問の価値がある）。
- 会話履歴に設計・実装の相談があれば、`references/format.md` の「AI との相談内容の要約」の規則に従う。コード全文は貼らず、再現に必要なパラメータやバージョンは削らない。

### 手順4: 書き込み、業務一覧を育てる

確認がとれたら `個人フォルダ/log/YYYY/YYYY-MM.md` の末尾に追記する。

**同じ日付の見出しが既にある場合**は日付見出しを新しく作らず、既存の見出しに統合する。`tags:` 行は重複させず、新しいタグだけ既存行の末尾に足す。既存セクションがあればその末尾に項目を足す。時刻は記入しない。

そのうえで、**返答の中に `個人業務一覧.md` のどのタグにも当てはまらない作業があったら、必ずユーザーに確認する。**

> 「『共同利用の査読対応』は業務一覧にありませんでした。新しい業務として追加しますか？（頻度・時期・関係者だけ教えてください）」

これは省略しないこと。引き継ぎ漏れの正体は「無意識化していて、本人が業務だと認識していない作業」であり、それが表に出る唯一の瞬間がここ。一覧が育つかどうかで、この skill の価値の大半が決まる。

追加時の注意:

- **タグは `#業務グループ/個別業務` の2階層で付ける。** 第1階層はタグ辞書の固定語彙から選ぶ。該当するグループが無ければ第1階層を空にせず、ユーザーに確認する。
- **タグ辞書に無い第1階層を勝手に作らない。** 必要なら「未登録」として個人業務一覧に記し、月次マージで正式採用する旨を伝える。
- **「関係者」列は必ず埋める。** 自分だけなら「単独」。この欄は後から遡って再構成できないため、空欄のまま流さない。
- 手順書の在りかが無く自分しか知らない業務なら、属人度を「高」にして備考に「未文書化」と書く。
- 「状態」は既定で「現行」。
- **判断レベル**は既定で空欄。新規の業務に関わり始めた場合は、次項の目安から推定して提案する。

**記録の対象の作業でファイルを作った・更新した場合**（作業項目のリスト、設計メモ、比較表、配布資料など）は、ファイルを `files/` に置き、ログにはパスを書く。中身はログに書き写さない。置き方は「ファイル管理」の節に従う。

### 手順5: 判断レベルの変化を検知する

`個人業務一覧.md` の「判断レベル」列（L1〜L5）は、その業務の**判断をどこまで任されているか**を表す。
定義は `references/format.md` の「判断レベル」の項にある。

**ユーザーに直接聞かない。** 返答や会話履歴に現れた事実から推定し、変化がありそうなときだけ提案する。

判定に使うのは、能力の印象ではなく次の事実だけ:

| 記録に現れた事実 | 示す段階 |
|---|---|
| 立ち会った・説明を受けた・見せてもらった | L1 |
| 〈経験者〉と一緒に作業した／指示を受けて実施した | L2 |
| 単独で着手し、途中で〈誰か〉に相談した／確認をとった | L3 |
| 単独で判断し完結した（相談の記述がない） | L4 |
| 〈後輩・後任〉と一緒に作業した／教えた／手順を説明した | L5 |

提案の仕方:

> 「この作業は相談なしで完結されたようなので、#受信機/FOREST運用 の判断レベルを L3 から L4 に上げますか？」

規則:

- **提案であって判定ではない。** 本人が「まだ相談したい」と言えばそのままにする。異論があれば即座に引き下がる。
- **1回の記録で断定しない。** 「単独で完結」が1件あっただけでは L4 と見なさない。同種の記録が複数回現れてから提案する。年に数回しか発生しない業務なら、その頻度に見合った回数でよい。
- **下げる提案はしない。** 相談した記録が出ても L4 → L3 とは提案しない。相談することは L4 と両立する。
- **論評しない。** 「成長されましたね」「順調ですね」の類は言わない。事実と提案だけを述べる。
- **変化がなければ何も言わない。** 毎回レベルの話をすると、記録が査定の場に見えてくる。
- 越境（他チーム・他装置の業務に初めて関わった）を検知したら、業務一覧に新しい行を L1 または L2 で追加することを提案する。**流動化の記録はここでしか残らない。**

### トラブル記録の場合

障害・不具合の対応だった場合は、日次ログに1行残したうえで **`共有/トラブル/YYYY-MM-DD-<短い件名>.md`** に独立ファイルを作る（個人フォルダではない。装置の記録であり、次に同じ事象に当たる人が読むため）。

聞くべきは **症状・最初の見立て・調査の経緯・原因・対処・次回のために**。原因が未確定でも書く（未確定であることも情報）。`status:` を正しく設定する。

**責任の所在は記録しない。** 誰の判断が悪かったかを書く欄は設けない。記録するのは事象と対処だけ。

#### 「最初の見立て」の扱い

調べ始める前に何を疑ったか、その見立てが当たったか外れたか、外れたならなぜずれたかを記録する。

- **外れた見立てのほうが価値が高い。** 「この装置は人をこう騙す」という形の知識になり、別の事象にも移植が効く。当たった場合は1行でよい。
- **この会話の中で対応していたなら、履歴の冒頭から拾う。** 結果を知る前の発言が残っているので、聞き直すより精度が高い。
- **書きにくそうなら空欄で通す。** 促さない。この欄は責任を問わない前提でしか成立せず、それを担保するのは運用であってテンプレートではない。空欄が続くなら欄の問題ではなく場の問題なので、記録を急かさない。
- ずれた理由は「なぜその見立てに至ったか」まで書けると効く。「前回の類似事例に引きずられた」「エラーが出ていないので正常系だと判断した」など。これが次に違う事象に当たった人への手がかりになる。

## 検索モード

### 手順

1. **`共有/タグ辞書.md` を読む。** ユーザーの質問語彙とログ内のタグは一致しないことが多い（「解析の高速化の件」→ `#計算機/解析パイプライン`）。辞書が対応表になる。**別名欄・旧称欄を必ず見る** — 改名されたタグは過去ログでは旧称のままになっている。
2. **期間を絞る。** 蓄積が増えるほど、期間の絞り込みが精度を決める。時期の手がかりが無ければ「いつ頃の話でしょうか」と一問聞いてよい。年フォルダ（`log/YYYY/`）で探索範囲を限定する。
3. **数年前の話なら、まず年次サマリを読む。** `log/YYYY/年次サマリ.md` があれば先にそれを読み、当たりを付けてから生ログに降りる。いきなり全月ファイルを読もうとしない。
4. **絞り込む。** `rg` でタグ・キーワードを検索する。日本語なので表記ゆれ（カタカナ/英字、送り仮名）を2〜3パターン試す。ヒットしなければキーワードを広げて再試行する。
5. **該当ファイルを Read する。** 月ファイル単位で読めば前後の文脈も入る。
6. **要約して答える。**

トラブルの照会は `共有/トラブル/` のファイル名一覧を先に見る。件名が具体的なので、これが最も精度の高い絞り込みになる。

**資料の照会**（「あのときの作業項目」「〇〇の設計メモ」）は、`共有/業務ノート/` と自分の `files/<業務グループ>/<個別業務>/` を見る。`files/` はタグと同じ 2 階層なので、タグ辞書で当たりを付けたフォルダを `ls` すれば足りる。キーワードで探すときは `rg` の対象に `files/` も含める。

### 答えるときの規則

- **必ず出典を添える。** 「2026-08-17 のログ」「共有/トラブル/2024-12-03-局発ロック外れ.md」のように日付とファイルを示す。原文を確認できることが、ログを信頼して使い続ける条件になる。
- **記録が無いことは「無い」と言う。** 曖昧な記憶で補完しない。「2025年度のログにこの件の記載はありませんでした」は有用な回答。
- **年度末報告書用の集計を求められたら**、期間内の全月ファイルを読み、タグ単位で束ねて出す。時系列の羅列ではなく業務ごとにまとめる方が報告書の構造に合う。1年を超える範囲なら年次サマリを使う。

## 棚卸しモード

### 業務一覧の点検

属人度「高」かつ手順欄が空の行を抽出して見せる。これが引き継ぎ事故の予備軍で、手順書を書くべき優先順位そのものになる。「関係者」が空欄の行があれば、あわせて埋めるよう促す。

**あわせて、判断レベルが L4/L5 で関係者が「単独」の行も抽出する。**
こちらは手順書があっても埋まらない穴で、性質が違う。

- 属人度「高」＋手順が空 → **手順を書けば**解消する
- L4/L5 ＋単独 → **人を張って経験させないと**解消しない

後者を解消するには、その業務に二人目を L1/L2 で入れる必要がある。
「手順書を書きましょう」では対処できない種類のリスクなので、混ぜずに別立てで示す。

**手順欄が空の行について、自分の `files/<業務グループ>/<個別業務>/` に資料があれば、あわせて示す。** 業務ノートへの書き出し（「ファイル管理」の節）の候補になる。資料が既にあるなら、手順書を一から書くより安く手順欄を埋められる。

### 引き継ぎ資料の生成

特定のタグについて、以下を束ねて `共有/引き継ぎ/<タグ名>-YYYY-MM.md` にまとめる。

- 業務一覧の該当行（頻度・時期・手順の在りか・関係者・属人度・判断レベル）
- 過去ログでその業務に触れた記述の要約
- 関連するトラブル記録へのリンク
- **年1回しか発生しない業務**（後任が最も困る）
- **未解決のまま残っている項目**
- **判断を要する場面と、任せられている範囲**

最後の3つは必ず含める。

最後の項目は、過去ログとトラブル記録から「手順書だけでは決まらなかった判断」を拾って書く。
判断の分岐が実際に現れているのは、トラブル記録の「経緯・調査」と「最初の見立て」、
日次ログの「決めたこと」の3か所。ここから、後任が単独では決められないであろう論点を列挙する。

前任者の判断レベルが L4/L5 なら、後任は必ずそれより低い段階から始まる。
**その差をどう埋めるか（誰に相談できるか）を書いていない引き継ぎ資料は、形式が整っていても機能しない。**
相談先が確保できていない場合は、それ自体を課題として明記する。

**これは生成物であり、個人ログの原文は含めない。** 要約された内容だけを出す。書き出す前にユーザーに内容を確認してもらう。

### 業務の棚卸し

一覧を見ながら、頻度と属人度から「やめる・任せる・自動化する」の候補を提示する。効率改善の材料はここから出る。

## ファイル管理

業務中に作ったファイル（作業項目のリスト、設計メモ、打ち合わせメモ、比較表、配布資料など）の置き場と、共有への書き出しの流れ。

ファイルには段階がある。自分用の走り書きから、業務を体系的に示して他人に渡す価値のあるものまで。**まず個人の `files/` に置き、まとまってきたら共有の業務ノートへ書き出す。** 下書きは個人、他人が読むものは共有、という worklog 全体の分け方と同じ。

### 置き場所

```
個人フォルダ/files/<業務グループ>/<個別業務>/
```

- **フォルダはタグの 2 階層にそろえる。** `#分光計/RFSoC分光計開発` の資料は `files/分光計/RFSoC分光計開発/`。ログの `tags:` と同じ語なので、タグから資料まで同じ手がかりで届く
- タグ辞書に未登録の業務グループも、タグどおりの名前でフォルダを作ってよい。正式採用で名前が変わったら、フォルダも合わせて改名する
- **業務グループ名に場所名・アンテナ名を入れない規則はフォルダにも適用する。** 「45m」などはファイル名の側に入れる
- 業務一覧に無い作業のファイルなら、まず記録モード手順4のとおり業務一覧への追加を確認してから置く
- **`files/` は個人フォルダの一部であり、本人のみが読む。** 月次マージでも開かない

### ファイル名

| 種類 | 名前の付け方 | 例 |
|---|---|---|
| 更新し続けるもの（作業項目、設計メモ、手順の下書き） | 固定の名前 | `45m設置作業項目.md` |
| その時点の記録（打ち合わせメモ、ある日の状態の写し） | 日付を頭に付ける | `2026-11-04_光ファイバー調査.md` |

- 形式は **Markdown を既定**にする。エディタで直せて、`rg` で探せて、この仕組みをやめても残る。作業項目は `- [ ]` のチェックリストで書く
- 他のアプリ向けのファイル（.pptx・.xlsx・.pdf など）もそのまま置いてよい。ただし検索に乗らないので、ログか同じフォルダの Markdown から一言で参照しておく

### 正本の決め方

- **正本はファイル。** Claude のドキュメントやアーティファクトはリンクがあれば別のチャットからも読めるが、`rg` の検索に乗らず、リンクを知らない新しいチャットからは見つけられず、claude.ai の外に残らない。使うなら一時的な表示と割り切り、正本は `files/` の Markdown に置く。ドキュメントで作ったものは、区切りのよいところで Markdown に書き出して正本を移し、以後はファイルを直す
- **ログからはパスで参照する**（`files/分光計/RFSoC分光計開発/45m設置作業項目.md`）。中身をログに書き写さない
- **コードの設計判断はリポジトリに置く。** ADR・仕様・手順書がリポジトリにある業務では、`files/` に置くのは業務の進め方や作業メモだけにする。リポジトリへ移すべき決定（設計の判断）を見つけたら、その旨を一言伝える

### 共有の業務ノートへの書き出し

`共有/業務ノート/<個別業務>.md` へ書き出す。業務ノートは個別業務の単位で 1 ファイル（既存の例: `連続波バックエンド.md`・`宿舎運用.md`）。

**書き出しを提案する合図:**

- 他の人が読む必要が出た（協力者が加わる、問い合わせが来る）
- 二人目を張る（業務一覧で L4/L5 ＋単独の行に人が入る）
- 業務一覧の「手順・資料の在りか」を埋めたい（棚卸しモードの点検で見つかる）

合図があっても提案にとどめ、書き出すかどうかは本人が決める。

**手順:**

1. `files/` の該当フォルダを読み、他人に渡す価値のある部分（手順・判断の分かれ目・決まったこと）を選ぶ。自分用の走り書きや途中の検討は持ち出さない
2. 業務ノートの下書きを会話に表示して確認をとる。既に業務ノートがあれば、その節に統合する
3. 書き込んだら、**個人側の元ファイルの先頭に 1 行**書く: `> → 共有/業務ノート/<個別業務>.md へ移した（YYYY-MM-DD）。以後は共有側を直す`。元ファイルは消さない
4. 業務一覧の「手順・資料の在りか」を共有側のパスに更新する
5. その日のログの「やったこと」に 1 行残す

書き出した後は共有側だけを直す（絶対に守ること 8）。

## 年次サマリ（年度末・年1回）

長期運用で最も重要な作業。生ログは数年分になると一度に読み切れなくなるため、年単位で圧縮した要約を残す。年度末報告書の作成とセットで行う。

`個人フォルダ/log/YYYY/年次サマリ.md` を生成する。手順:

1. その年度の全月ファイルを読む
2. タグ単位で束ねる（時系列に並べない）
3. `references/format.md` の年次サマリの書式に従って要約する
4. ユーザーに確認してもらう
5. 確認後、**本人が共有側に出すかどうかを尋ねる。** 原本は個人フォルダに残す

未解決のまま年度を越える項目は必ず残す。

あわせて次の2節を作る。どちらも**年単位で並べて初めて見えるもの**で、ここが年次サマリの効きどころ。

- **判断レベルの変化** — 年度内に動いた行を事実として列挙する。動かなかったものには触れない。
  ここで書く価値があるのは **L4/L5 が自分ひとりのまま年度を越えた業務**で、
  翌年度に渡す相手を探すべき対象になる
- **外した見立ての傾向** — その年度のトラブル記録の「最初の見立て」を束ね、
  外れ方に共通の型がないかを見る。単発では癖と偶然が区別できないが、
  年単位なら分離できる。該当が無い年は節ごと省く

**この2節は本人の材料であって、報告用ではない。** 共有側に出す判断は本人に委ね、
出さない選択をした場合もそれ以上勧めない。

## 月次マージ（マージ担当のみ）

**このモードは、CONFIG.md に `役割: マージ担当` と書かれている場合のみ実行する。** 書かれていなければ「この作業はマージ担当の方が実施します」と伝えて実行しない。

マージ担当は集約のために各自の `個人業務一覧.md` を読む必要がある（日次ログは読まない）。手順:

1. 各メンバーの `個人業務一覧.md` を読む（**`log/`・`trouble/`・`files/` は開かない**）
2. 業務グループごとに `共有/業務グループ/<グループ名>.md` へ統合する。同一業務を複数人が担当している場合は関係者欄にまとめる
3. 「未登録」タグを一覧し、正式採用の可否をユーザーに確認して `共有/タグ辞書.md` に追加する
4. **属人度「高」かつ手順欄が空の行**を抽出して提示する。これが実質的な成果物
5. あわせて「関係者」が空欄の行も提示する
6. **判断レベルを業務単位で集約し、「L4 以上が一人しかいない業務」を抽出する**（次項）

同じ作業を複数人・複数の業務グループで別々に実施している兆候があれば指摘する。合理化の材料はここから出る。

### 判断レベルの集約

**集約するのは業務ごとの人数であって、個人の一覧ではない。** 出力はこの形にする。

```markdown
## 単独で判断できる人が一人しかいない業務

| 業務 | L4以上 | L2〜L3 | 備考 |
|---|---|---|---|
| #計算機/解析パイプライン | Aさん(L5) | なし | 二人目が不在。手順書はあるが判断の経験者がいない |
| #受信機/FOREST運用 | Bさん(L4) | Cさん(L3) | Cさんが L4 に届けば解消 |
```

これは属人度と同じ**組織側のリスク指標**として扱う。読み方:

- **L4 以上がゼロまたは一人の業務が、その部門の脆弱点。** 手順書の有無とは独立した指標で、
  手順書が完備していても、判断を任せられる人が一人なら引き継ぎは成立していない
- **L2〜L3 の欄が空の業務は、後継が育っていない。** 逆にここに名前があれば、
  数年内に解消する見込みが立つ。二人目を張るべき業務の優先順位はここから決まる
- **L1・L2 の行が増えていることは良い兆候。** 越境が起きている証拠であり、
  減っている業務グループがあれば、そこが孤立し始めている

**やらないこと:**

- **個人ごとの一覧を作らない。** 「誰が何レベルを何個持っているか」の表は作らない。
  縦に人を並べた瞬間に、この列は査定表になる
- **レベルの低さを問題として提示しない。** 提示するのは業務側の穴だけ。
  「Aさんは L1 が多い」ではなく「この業務は L4 が一人」と書く
- **人事評価・実績比較の資料としては出さない。** 求められた場合は、
  この列がその用途を想定していないこと（低いことが正常な状態を含むこと）を伝える

## 続けてもらうための原則

利用者は過去に何度かログが続かなかった経験がある。記録の質より継続を優先する場面が多い。

- **空いた日を埋めさせない。** 3日分まとめて聞き出そうとしない。思い出せない記録は精度が低く、それを書くこと自体が苦役になって離脱を招く。「今日の分だけ」でよい。
- **短い記録を歓迎する。** 「やったこと2行だけ」の日があってよい。書く量で価値が決まるわけではない。
- **説教しない。** 数日空いても指摘しない。再開したことを普通に受け止めて進める。「最近書けていませんね」の類は言わない。
- **記録の頻度を一定に保とうとしない。** 濃い日は3回、何もない日は0回でよい。均そうとした瞬間に、書くことのない日を埋める作業が発生して負担になる。
- **たまに効用を見せる。** 検索モードで過去の記録が役に立った瞬間は、続ける動機が最も強くなるタイミング。「2024年に同じ事象の記録がありました」と出せたときは、それが記録の成果であることが伝わるように答える。
- **外れた見立てを、失敗として扱わない。** かといって「良い記録ですね」と持ち上げもしない。他の記述と同じ調子で淡々と書く。特別扱いした時点で、その欄は書きにくくなる。
- **評価と結びつけない。** 日々のログ、トラブル記録、見立ての記録が人事評価や実績比較に使われることはない。

  判断レベルの列だけは月次マージで集約されるが、集約の単位は**業務**であって人ではない。
  見るのは「この業務を単独で判断できる人が何人いるか」という組織側の穴で、
  個人ごとの一覧は作らない。**低いことは正常な状態を含む**（新しい業務に関わり始めれば L1 から始まり、
  越境が進むほど L1・L2 は増える）ため、そもそも序列の指標として成立しない。

  ユーザーがこの点を気にする素振りを見せたら、上をそのまま伝えてよい。
  **懸念を軽く扱わない。** この仕組みが続くかどうかは、率直に書けるかどうかにかかっており、
  評価に使われるという疑いが一度でも立つと、記録は防衛的になって価値を失う。
  疑いが残るようなら、判断レベルの記入を止めることを選択肢として提示してよい。この列は無くても他は機能する。

# 書式仕様

この書式は二つの制約の妥協点として決めてある。

1. **AI が検索・要約しやすい** — 固定の見出し、行頭のタグ行、日付の統一表記。`rg` で機械的に絞り込め、Read で読む範囲を月単位に限定できる。
2. **人間が読める・編集できる** — 素の Markdown。エディタで直接直せる。将来この skill を使わなくなっても資産が残る。

JSON や YAML でないのは、ユーザーが手で直せなくなると資産が腐るため。逆に完全な自由記述でないのは、蓄積後に AI が絞り込めなくなるため。

---

## ディレクトリ構成

```
<WORKLOG_ROOT>/
├── 共有/
│   ├── タグ辞書.md                     タグ語彙のマスタ
│   ├── 業務グループ/
│   │   ├── 受信機.md                   月次マージで生成
│   │   └── …
│   ├── トラブル/
│   │   └── 2026-08-17-受信機出力異常.md
│   └── 引き継ぎ/
│       └── 受信機-FOREST運用-2026-08.md
└── 個人/
    ├── <氏名>/
    │   ├── CONFIG.md
    │   ├── 個人業務一覧.md
    │   └── log/2026/
    │       ├── 2026-08.md              日次ログ（月1ファイル・追記型）
    │       └── 年次サマリ.md            年度末に生成
    └── _アーカイブ/
```

**個人フォルダは本人のみが読み書きする。** 他人の個人フォルダを開かない。例外は月次マージ時の `個人業務一覧.md` のみで、`log/` は対象外。

トラブル記録が共有側にあるのは、内容が個人の記録ではなく**装置の記録**であり、次に同じ事象に当たる人が読むことが存在理由だから。

月1ファイルにしてあるのは、Read 一回で1か月分が読める粒度だから。日別ファイルだと検索時にファイルを何十回も開くことになり、年別ファイルだと1回の読み込みが重くなりすぎる。

## 1. タグ

### 2階層タグ

`#業務グループ/個別業務` の形式を使う。

```
#受信機/FOREST運用
#計算機/解析パイプライン
#広報/施設公開
```

- **第1階層（業務グループ）** — 固定語彙。`共有/タグ辞書.md` から選ぶ。勝手に増やさない
- **第2階層（個別業務）** — 必要に応じて追加してよい

第1階層を固定することで、第2階層の語彙がブレても必ず束ねられる。

### 命名の禁止事項

**業務グループ名にアンテナ名・場所名を含めない。** `#45m受信機` のような名前を作らないこと。将来「装置種別」軸と「アンテナ」軸を別の軸として分離するため、混ぜると分離不能になる。

### タグ辞書（`共有/タグ辞書.md`）

語彙のマスタ。**この skill から勝手に編集しない。** 新しいタグが必要になったら、個人業務一覧に「未登録」として記録するだけにとどめ、月次マージで管理担当が正式採用する。

辞書には別名・旧称の欄がある。タグを改名しても過去ログは書き換えず、旧称を別名欄に足すことで新旧を繋ぐ。**検索時は必ず別名欄を見ること。**

有効期間・後継タグの欄は、装置の世代交代に対応するためのもの。同じ名前が数年後に別の実体を指すようになるため。

## 2. 日次ログ（`個人/<氏名>/log/YYYY/YYYY-MM.md`）

月ファイルの先頭は一度だけ:

```markdown
# 業務ログ 2026-08
```

以降、新しい日を **末尾に追記**する（時系列が自然に読めるため）。

```markdown
## 2026-08-17 (月)
tags: #受信機/FOREST運用 #計算機/解析パイプライン

### やったこと
- FOREST の受信機ログを確認、8/14 のスパイクを再確認
- 解析パイプラインのベースライン差し引きを polyfit → asinh 近似に変更

### 決めたこと
- **決定**: ベースライン推定を asinh 近似に変更した
  **理由**: 強い輝線が乗る領域で polyfit が引きずられ、裾が沈む問題があったため
  **見送った案**: マスク領域を手動指定する案。観測ごとに手作業が発生し運用に乗らないと判断

### 詰まった点・未解決
- スパイクの原因が装置側かソフト側か切り分けできていない。8/20 の保守時に要確認

### 次にやること
- [ ] 保守時に受信機の温度ログを取得する
```

### 規則

- **中身のないセクションは書かない。** 空の見出しは検索ノイズになるだけ。「やったこと」だけの日があってよい。
- **一日に複数回記録する場合も、日付見出しは一つに保つ。** 2回目以降は既存セクションに項目を足し、`tags:` 行には新しいタグだけを追記する。時刻は記入しない（検索の役に立たず手間だけ増える）。
- **`tags:` 行は `##` 見出しの直下に必ず置く。** これが検索の主キー。
- 「決めたこと」は **決定・理由・見送った案** の3点セットで書く。半年後に効いてくるのは決定そのものより「なぜ他の案を採らなかったか」で、これが無いと同じ議論を繰り返す。
- 未解決事項は消さずに残す。後日解決したら、その日のログに「8/17 の未解決の件が解決」と書いて繋ぐ。
- **作業時間・工数は書かない。**

## 3. AI との相談内容の要約

同じ会話の中で仕様設計やコード実装を相談していた場合、その結論をログに落とす。ここが記憶に頼れない部分で、書く価値が最も高い。

`### 決めたこと` に含めるか、量が多ければ専用セクションを立てる:

```markdown
### 設計・実装（AI相談）
- **対象**: `~/git/nro-pipeline/baseline.py` の `fit_baseline()`
- **決定**: 窓幅を固定 128ch から、輝線幅の 3 倍の可変窓に変更
  **理由**: 分子雲コアと外縁で線幅が一桁違い、固定窓ではどちらかが必ず破綻するため
  **見送った案**: チャンネル数を観測モードごとに設定ファイルで持つ案。設定の分岐が増え保守が重くなる
- **再現に必要な情報**: numpy 2.1 / scipy 1.14。`fit_baseline(spec, width_factor=3.0)` で従来挙動は `width_factor=None`
```

### 規則

- **コードの全文は貼らない。** ファイルパス・関数名・変更の要点だけ書く。ログにコードを貼ると、コードが変わったときにログが嘘になる。
- **再現に必要な情報は削らない。** ライブラリのバージョン、実行コマンド、パラメータ値、データのパス。半年後に困るのは決まってここ。
- 相談の過程は要らない。**結論と、その結論に至った理由**だけを残す。

## 4. 業務一覧（`個人業務一覧.md` / `共有/業務グループ/<名>.md`）

引き継ぎ漏れ対策の中核。日次ログ（フロー型）では、年1回しか発生しない業務は年1行しか現れず、引き継ぎ時に拾えない。一覧（ストック型）を別に持ち、ログを書くたびに育てる。

```markdown
| タグ | 業務名 | 分類 | 頻度 | 時期・期限 | 手順・資料の在りか | 関係者 | 属人度 | 判断レベル | 状態 | 備考 |
|---|---|---|---|---|---|---|---|---|---|---|
| #受信機/FOREST運用 | FOREST受信機の運用対応 | 装置 | 随時 | 観測期(11-4月) | ~/nro-work/forest/manual.md | Bさん, Cさん | 高 | L4 | 現行 | 立ち上げ手順が未文書化 |
| #計算機/解析パイプライン | 共同利用データ解析パイプラインの保守 | 開発 | 週数回 | - | ~/git/nro-pipeline/README.md | 単独 | 高 | L5 | 現行 | |
| #分光計/立ち上げ調整 | 分光計の立ち上げ調整（越境して参加中） | 装置 | 観測期前 | 10月 | Cさんの手順書 | Cさん(主), 自分 | 低 | L2 | 現行 | 2026年度から参加 |
| #広報/年度末報告 | 年度末業績報告の作成 | 事務 | 年1回 | 3月 | 前年度ファイル参照 | 事務局 | 中 | L3 | 現行 | |
```

### 列の意味

- **タグ** — 日次ログの `tags:` 行と一致させる。ここが一致していないと検索が繋がらない
- **頻度・時期** — 引き継ぎ時に「いつ発生するか」が最重要。年1回の業務ほど漏れる
- **関係者** — **必ず埋める。** 自分だけなら「単独」。人員が増えたあとでは遡って再構成できない情報
- **属人度（高/中/低）** — **業務の側**から見て、現状どれだけ一人に集中しているか。**高 かつ 手順が未文書化のものが引き継ぎ事故の予備軍**
- **判断レベル（L1〜L5）** — **人の側**から見て、その業務の判断をどこまで任されているか（次項）
- **手順・資料の在りか** — 空欄なら「記憶の中にしかない」ということ。空欄の多さがそのまま引き継ぎリスクの量
- **状態（現行/終了）** — 終了した業務も行を削除しない。備考に終了年を記す。履歴が切れると経緯を追えなくなる

### 判断レベル（L1〜L5）

医学教育の EPA（Entrustable Professional Activities）の考え方を借りたもの。
**「何を知っているか」ではなく「監督なしで任せられるか」** で段階を定める。
保守業務では、知識の量より「単独で判断してよい範囲」のほうが実態に近いため。

| | 状態 | 判定の目安（記録から読み取れる事実） |
|---|---|---|
| L1 | 見学のみ。単独では実施しない | 立ち会った・説明を受けた |
| L2 | 監督下で実施。判断は経験者が行う | 経験者と一緒に作業した |
| L3 | 単独で実施するが、判断に迷えば相談する | 単独で着手し、途中で相談した |
| L4 | 単独で判断し完結できる | 相談なしで完結した |
| L5 | 他者に教え、他者の判断を監督できる | 後任・後輩と一緒に作業した／説明した |

属人度と判断レベルは、同じ事実を両側から見たもの。属人度は「渡せていない度合い」、
判断レベルは「受け取った度合い」。引き継ぎが進むと、渡す側の属人度が下がり、
受け取る側の判断レベルが上がる。**この2列が同時に動くのが、引き継ぎが成立した状態。**

この列を置く理由は、手順の文書化では埋まらない穴があるため。
手順書が完備していても、その業務の判断を任せられる人が一人しかいなければ引き継ぎは成立しない。
属人度だけを見ていると、この穴は「手順書があるから大丈夫」に見えてしまう。

**低いことは問題ではない。** 新しい業務に関わり始めれば L1 から始まる。それが正常。
流動化を進めるほど L1・L2 の行は増える。増えていること自体が、越境が起きている証拠になる。

**人事評価の資料ではない。** 月次マージで集約するのは、業務ごとに
「単独で判断できる人が何人いるか」を見るため。個人の序列をつけるためではない。
属人度と同じく、**組織側のリスク指標**として扱う。

### 更新のタイミング

- 日次ログを書くとき、既存タグに当てはまらない作業が出てきたら追加する
- 属人度「高」で手順欄が空の行を見つけたら、ユーザーに一言伝える（手順書を書く動機づけになる）
- 記録の中に判断レベルの変化を示す事実（誰と作業したか、判断を誰がしたか）が現れたら、
  変更を**提案**する。書き換えるのは本人の確認後。詳細は SKILL.md の記録モードに従う

## 5. トラブル記録（`共有/トラブル/YYYY-MM-DD-<短い件名>.md`）

日次ログに埋めず独立ファイルにするのは、トラブル対応時に「過去の同種案件だけ」を素早く並べたいため。年に数回しか発生しないので、発生時だけ書けばよい。

```markdown
# 2026-08-17 受信機の出力異常
tags: #受信機/FOREST運用
status: 暫定対処
発生日: 2026-08-17
解決日: -

## 症状
20時頃から IF2 系統の出力が通常の 0.3 倍程度に低下。他系統は正常。

## 最初の見立て
- 見立て: ケーブルの接触不良。前回の同種の症状がそうだったため
- 結果: 外れ
- ずれた理由: 前回の事例に引きずられた。他系統が正常＝共通部位ではない、という点までは合っていたが、
  「1系統だけ」で真っ先にケーブルを疑ったのは早すぎた。温度ログを先に見れば10分で当たっていた

## 経緯・調査
1. ケーブル接続を確認 → 異常なし
2. 温度ログを確認 → 局発部が通常より 4K 高い
3. 局発を再起動 → 出力が一時的に回復、2時間後に再発

## 原因
局発部の温度上昇が疑わしいが、未確定。

## 対処
当該観測は IF2 を除外して継続。8/20 の保守で冷凍機を点検予定。

## 再発防止・次回のために
- 温度ログの監視閾値が現状 +6K で、今回の +4K では警報が出なかった。閾値の見直しを検討
- 局発の再起動手順: `~/nro-work/forest/restart_lo.sh`（要 sudo、観測停止が必要）

## 参照
- 過去の類似案件: 共有/トラブル/2024-12-03-局発ロック外れ.md
```

### 規則

- `status:` は **解決済 / 暫定対処 / 未解決** の3値。未解決のまま放置されている案件を後から拾えるようにするため。**未解決は正常な状態**であり、原因が未確定でも記録する。
- **責任の所在は書かない。** 「誰の判断が悪かったか」を記録する欄は設けない。記録するのは事象と対処だけ。これが無いと書きづらくなり、記録されなくなる。
- 「再発防止・次回のために」が最も価値のあるセクション。**次に同じことが起きた人（自分含む）が最初に読む場所**として書く。

### 「最初の見立て」について

この記録には読者が二人いる。

1. **次に同じ事象に当たる人** — 経緯・調査と再発防止を読む。答えが要る
2. **次に違う事象に当たる人** — 答えは役に立たない。要るのは切り分けの型

「経緯・調査」は一人目のためのもので、成功した経路だけが整然と残る。
だが実際の判断は袋小路を含んでおり、そこが消えると二人目には何も残らない。
「最初の見立て」はその二人目のための欄。

- **外れた見立てのほうが価値が高い。** 「この装置は人をこう騙す」という形の知識になり、
  同じ装置の別の事象、さらには別の装置にも移植が効く
- **書きにくければ空欄でよい。** 責任を問わない欄だが、それは運用で担保するしかない。
  空欄が続くようなら欄ではなく場の問題なので、埋めるよう促さない
- 蓄積すると、年次サマリで「外した見立ての傾向」として束ねられる。個人の癖と、
  装置側の紛らわしさの両方が見えてくる
- ファイル名の件名は日本語でよいが、短く（20字以内）。ファイル名の一覧性は、蓄積が増えても精度が落ちない唯一の検索手段になる。
- 日次ログには1行だけ残し、詳細はこちらに書く。

## 6. 年次サマリ（`個人/<氏名>/log/YYYY/年次サマリ.md`）

数年分の生ログは一度に読み切れないため、年単位で圧縮した要約を残す。長期の照会はまずこれを読み、必要なときだけ生ログに降りる。

```markdown
# 年次サマリ 2026年度

作成日: 2027-03-25

## #受信機/FOREST運用
- 観測期を通じて運用対応。大きな構成変更なし
- **決めたこと**: 局発の再起動手順を文書化し `restart_lo.sh` に集約した（理由: 手順が口伝で、担当者不在時に対応できなかったため）
- **未解決（翌年度へ）**: IF2 系統のスパイクの原因が装置側かソフト側か未切り分け
- トラブル: 2件（8/17 出力異常=暫定対処、12/3 局発ロック外れ=解決済）

## #計算機/解析パイプライン
- ベースライン推定を polyfit から asinh 近似へ変更
- **決めたこと**: 窓幅を可変化（理由: 分子雲コアと外縁で線幅が一桁違い、固定窓では破綻するため）
- **未解決**: なし

## 業務一覧の変化
- 追加: #広報/施設公開（年1回・10月）
- 終了: なし

## 判断レベルの変化
- #受信機/FOREST運用: L3 → L4（10月の立ち上げを単独で完結）
- #分光計/立ち上げ調整: — → L2（2026年度から参加。Cさんの監督下）
- #計算機/解析パイプライン: L5 のまま。**この業務を単独判断できるのは依然として自分のみ**

## 外した見立ての傾向
- トラブル3件のうち2件で、前回の類似事例に引きずられた見立てを立てていた
  （8/17 出力異常、12/3 局発ロック外れ）。症状の見た目が似ていても、
  先に安価な切り分け（温度ログ・Recv-Q など状態量の確認）を通すほうが速い
- 「エラーが出ていない＝正常系」と判断して遠回りした事例が1件
```

### 規則

- **時系列で並べない。タグ単位で束ねる。** 報告書の構造に合い、後の照会でも探しやすい
- **未解決のまま年度を越える項目は必ず残す。** 翌年度のサマリでも追跡できるようにする
- 決めたことは決定と理由を残す。見送った案は省いてよい（詳細は生ログにある）
- トラブルは件数と件名・status のみ。詳細は `共有/トラブル/` にある
- **「判断レベルの変化」は事実だけを書く。** 上がったことを称揚せず、上がらなかったことにも触れない。
  変化がなければ「変化なし」でよい。ここで書く価値があるのは、
  **L4/L5 が自分ひとりのまま年度を越えた業務**で、これは翌年度に渡す相手を探すべき対象になる
- **「外した見立ての傾向」は年次サマリでのみ束ねる。** 単発の記録では傾向は見えず、
  年単位で並べて初めて自分の癖と装置側の紛らわしさが分離できる。ここがこの欄の効きどころ。
  該当が無い年は節ごと省いてよい
- 生成物であり、本人の確認を経て共有側に出す。原本は個人フォルダに残す

## 7. 引き継ぎ資料（`共有/引き継ぎ/<タグ名>-YYYY-MM.md`）

棚卸しモードで生成する。**個人ログの原文は含めない。要約された内容だけを出す。**

```markdown
# 引き継ぎ資料: #受信機/FOREST運用

作成日: 2027-03-25
作成者: 〈氏名〉

## 業務の概要
（業務一覧の該当行から: 業務名・分類・頻度・時期・関係者・属人度・判断レベル）

## 判断を要する場面と、任せられている範囲
- 現在の判断レベル: L4（単独で判断し完結している）
```
